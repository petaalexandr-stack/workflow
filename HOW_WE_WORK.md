# Как мы работаем над Workflow

## Цель и неизменные условия

Мы последовательно улучшаем локальный Workflow v0.7 для **Codex App**. Работа не требует от нас отдельного OpenAI API key, не опирается на Responses API. Источником истины служат репозиторий, проверяемые артефакты и фактические журналы, а не слова агента «completed».

Роли участников: **владелец** выполняет живые сценарии в своей версии Codex App и явно утверждает решения; **ревьюер** анализирует MD-отчёты, патчи, выявляет причину, предлагает точечное изменение; **Codex** выполняет только согласованную итерацию. Одна итерация — одна проверяемая гипотеза, один набор изменённых файлов, один отчёт.

## Цикл итерации

1. **Выбор задачи:** открыть `docs/ROADMAP.md`, прочитать конкретный этап, определить вход/выход и ограничения. Если предполагается новая архитектура — описать варианты до кода.
2. **Git:** ветка `work/<stage>-<short-name>`, исходный SHA, чистота дерева, рабочая папка совпадает с Git-корнем. Не править оригинальную историческую копию.
3. **Красный тест/репродукция:** воспроизвести проблему в fake-server или на локальном тестовом проекте; зафиксировать *ожидаемое vs фактическое*.
4. **Минимальное исправление:** менять только соответствующий слой (транспорт, контроллер, skill, модуль). Без массового рефакторинга или автоматического удаления файлов.
5. **Проверка:** unit/integration тесты, `git diff --check`, статус/дифф. Для требований к UI — реальная проверка с версией Codex App, а не только fake-server.
6. **Отчёт:** заполнить `reports/_TEMPLATE.md`, обезличить, приложить воспроизводимые команды, IDs при необходимости и вывод тестов. Если результат неизвестен, писать `не проверено`.
7. **Разбор:** классифицировать сбой: код workflow / транспорт Codex / настройка среды / UI / недостаточные требования. Решить: исправить ту же итерацию, откатиться или принять и идти дальше.
8. **Приёмка:** только после явно подтверждённого результата сливать PR в `main` и начинать следующую итерацию. Неуспешный модуль — не основание запускать следующий.

## Приоритеты и чёткая граница

На первой фазе **нельзя смешивать**: (A) нативный Codex App (один видимый чат + AGENTS/skill), (B) Codex CLI app-server Bridge (программное создание отдельных чатов), (C) прямой API-модельный провайдер. (C) вне нашей цели. Сравниваем A и B **на одной и той же задаче**. Если A закрывает требования — не усложнять систему Bridge без обоснования. Если нужны постоянные отдельные чаты и строгие детерминированные approval gates — сохранить Controller/Bridge и исправлять совместимость.

Первый тест: «Небольшая программа читает тестовый CSV продаж и считает выручку за месяц». На модуле 01 **код приложения не писать**, только получение краткого понимания, вопросов и статуса. Затем тот же кейс усложняем.

## Какие документы обязательны

- **`AGENTS.md`** — короткие правила разработки в Codex.
- **`HOW_WE_WORK.md`** — процедура одной итерации, приёмки и анализа отчётов.
- **`docs/ROADMAP.md`** — очерёдность работ и принятые решения.
- **`docs/ITERATION-01.md`** — текущее детальное ТЗ (в будущем — аналогичный файл для текущей итерации).
- **`reports/_TEMPLATE.md`** — формат фактического испытания; один обезличенный отчёт на прогон.
- **`docs/DECISIONS.md`** — решение оставить/удалить слой или изменить контракт.

Не нужно создавать по документу на каждый чат, каждую роль или каждое промежуточное сообщение. Результат модуля хранится один раз в структурированном handoff. Если требуется подробная история, она остаётся у Codex, а в Git — только сокращённые доказательства и ссылки/ID без секретов.

## Принцип удаления лишнего

Пока функция используется или может влиять на совместимость, она помечается `retain` или `defer`. Удаление — отдельный PR с анализом импортов, негативным тестом и подтверждением, что необходимая способность сохранена. См. `docs/FILE-AUDIT.md`.
