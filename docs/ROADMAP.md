# Roadmap: от стабильного входа до end-to-end

Статусы: `planned` — только предложено; `in_progress` — есть рабочий PR; `verified_offline` — тестовый сервер; `verified_live` — проверено в реальном Codex App; `accepted` — подтверждено владельцем. Нельзя повышать статус по отчёту агента без доказательств.

| Шаг | Название | Что проверяем | Что считаем готовым |
|---|---|---|---|
| 00 | Git + документы | сохранение v0.7, корневая структура, отчёты, AGENTS, тесты | репо клонируется, 31 офлайн-тест проходит после минимального исправления Windows command parsing, нет секретов |
| **01** | **Вход в Codex App / Orchestrator** | сравнение нативного чата и Bridge; transport, status, роль, UI | один видимый чат, нужная роль, правильные вопросы, нет дубликатов; live-отчёт |
| 02 | Understanding и согласования | вопросы → уточнения → утверждённое понимание | невозможно начать следующий шаг без явного утверждения |
| 03 | Route + Tasks | минимальный маршрут под маленькую задачу, inputs, декомпозиция | валидный маршрут, handoff и проверяемые задачи без разработки |
| 04 | Development | маленькая утилита CSV в изолированной ветке | реальные файлы + воспроизводимый тест + diff |
| 05 | Quality + Debugging | ошибки, исправление только дефектного участка, регрессия | tester/reviewer/security используют факты; повтор не портит готовое |
| 06 | Discovery (две роли) | Researcher → валидированный результат → UX | UX действительно получает данные Researcher, а не общий исходный текст |
| 07 | Evals + Planning | критерии качества и план по утверждённой задаче | результаты измеримы и не смешиваются с реализацией |
| 08 | System Design | light/full по сложности | конкретная архитектура с отмеченными допущениями |
| 09 | Documentation | аудит изменённых файлов и пользовательской документации | документы соответствуют фактическим diff и работе кода |
| 10 | End-to-end | тот же CSV: идея → задача → код → тест → docs; затем сложнее | каждый gate/артефакт обоснован, восстановление проверено |

Шаг 00 — подготовка репозитория и планов, **не исправление кода**. Шаг 01 оценивается в **4 основных итерации** и потенциально 1–2 корректирующих по live-отчётам. Все остальные оценки уточняются после измерения трудоёмкости первого этапа; это не гарантии сроков.

### Рабочие итерации шага 01

1. **01A — сравнительный минимальный запуск.** В нативном Codex App выполнить понимание идеи в текущем чате без Bridge; отдельно выполнить контролируемый запуск через текущий Bridge и записать различия. Цель — решить, действительно ли нужен автоматический `thread/start`.
2. **01B — протокол и права (если Bridge нужен).** Исправить несовместимые параметры Codex, preflight Windows/CLI; тестировать deny, read-only, error classifications.
3. **01C — resume и UI.** Сохранение роли/первого сообщения, `pending`, восстановление, подтверждённая UI-навигация или явный fallback.
4. **01D — приёмка.** Новый запуск + ошибка + восстановление, сохранение состояния, отчёт, `git diff`, тесты, решение владельца.

**Решение после 01A обязательно записать в `docs/DECISIONS.md`.** Удалять Bridge только при доказанной ненужности строгого controller/cross-chat FSM. И наоборот, не обещать нативному режиму автоматическую навигацию/внешнюю оркестрацию без инструментального подтверждения.

### Порядок тестирования самих модулей

Каждый модуль: `prepare` (вход и цель) → `execute` (одна роль или связанная цепочка ролей) → `verify` (схема, инструменты, тесты) → `review` (показать результат) → `approve` (значимое решение владельца). Если verify не пройден, адресно переделать неисправную роль и проверить снова, не инициируя следующий модуль.
