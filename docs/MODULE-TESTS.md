# Как проверяем модули (от простой задачи к сложной)

Контроллер v0.7 содержит 9 внешних модулей и 2 внутренних шага (`understanding`, `routing`). У каждого внешнего модуля по плану должны появиться проверяемые вход/выход, свидетельства реального действия и адресная доработка. Ниже — **предлагаемое** тестирование, не утверждение об уже реализованных функциях.

| Порядок | Модуль/шаг | Простейший сценарий | Доказательство | Усложнение |
|---|---|---|---|---|
| 1 | **Codex entry + Orchestrator** (инфраструктура) | объяснить задачу CSV без кода | читаемый чат, вопросы, состояние/ограничения | обрыв и продолжение |
| 2 | **Understanding** (внутренний) | ответы на вопросы и фиксация критериев | согласованный brief; нет самосогласования | конфликтующие уточнения |
| 3 | **Routing** (внутренний) | краткий минимальный список для CSV | входы от утверждённых шагов, gate | изменение маршрута |
| 4 | **Tasks** | составить 3–5 независимых проверяемых задач | задачи, зависимости и приёмка | исправление одной задачи |
| 5 | **Development** | написать CSV-парсер и CLI | реальные файлы, тесты, Git diff | пограничные значения, плохой CSV |
| 6 | **Quality** | reviewer → tester → security | реальные замечания, тесты, evidence | баги безопасности / регрессия |
| 7 | **Debugging** | воспроизвести ошибку месяца/суммы | красный тест → patch → зелёный тест | повторный сбой, selective revision |
| 8 | **Discovery** | исследовать 2–3 сценария пользователя CSV-утилиты | handoff Researcher, прочитанный UX Designer | несколько персонажей/контекстов |
| 9 | **Evals** | определить и измерить пограничные проверки | метрики, тестовые случаи | качество рекомендаций |
| 10 | **Planning** | спланировать следующий CSV-feature | этапы и критерии | изменение сроков/объёма |
| 11 | **System Design** | light: файловый CLI | архитектура и честные допущения | full: сервис/API/хранилище |
| 12 | **Documentation** | инструкции установки, тестов, примеры | соответствие docs реальному diff | повторный аудит всего task scope |
| 13 | **End-to-end** | идея → уточнение → route → код → тест → docs | журнал всех checkpoints и Git | исходная бизнес-система |

**Важное уточнение:** в исходном v0.7 `Documentation` обязателен как финальный модуль. Таблица выше — **порядок самостоятельных проверок модулей**, не маршрут одной пользовательской задачи. Реальный маршрут под задачу выбирается отдельно и должен быть минимальным.

## Внутренний протокол проверки одного модуля

1. `prepare`: задача, утверждённые inputs, выход, тестовые данные, версия контракта.
2. `execute`: ровно назначенная роль; если ролей несколько, отдельный промежуточный handoff между ними и проверка корректности.
3. `verify`: схема результата, наблюдаемые факты, реальный запуск тестов, проверка файлов/permissions. При blocked — указать почему.
4. `repair`: повторить только проблемную роль с минимальным feedback; не отменять хорошие результаты без причины.
5. `review`: человек видит что сделано, что не проверено, риски, изменения и решение.
6. `approve`: только явное человеческое утверждение; после него handoff immutable/версионирован.

**Не создавать** отдельные чаты и документы на каждый микрошаг по умолчанию: чат нужен только для роли/контекста, документ — только для самостоятельного проверяемого артефакта.
