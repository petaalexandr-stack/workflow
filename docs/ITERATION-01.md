# Этап 01 — вход в Codex App и понимание одной задачи

**Статус:** planned. **Модельный транспорт:** авторизованный Codex App / CLI, **не прямой API**. **В рамках этапа никакого кода CSV-приложения не создаём.** Исходный движок v0.7 на этом этапе рассматривается как baseline, не как уже исправленный продукт.

## Входные данные и ожидаемый результат

**Тестовая задача:** «Хочу небольшую Python-программу, которая читает CSV с продажами и показывает суммарную выручку за выбранный месяц. Сейчас только сформулируй понимание задачи, существенные вопросы, границы и проверяемые критерии. Не разрабатывай программу и не меняй файлы». Использовать ровно тот же текст в двух вариантах 01A.

Выход: точная формулировка задачи (без выдуманной предметной области), до нескольких существенных вопросов, ограничения, критерии приёмки и факт остановки до перехода к разработке. Для Bridge — статус `await_clarification` или `await_understanding` по содержимому идеи, `run_id` и `thread_id`. Для нативного сценария нет и не должно быть выдуманного controller-status.

### Два независимых варианта 01A

| | Нативный Codex App | Python Bridge v0.7 |
|---|---|---|
| Где запускается | в текущем открытом чате Codex App по `AGENTS.md` и пользовательскому заданию | CLI → Codex app-server `thread/start` / `turn/start` |
| Плюсы | меньше слоёв, проще UI и контекст, быстрее проверка | отдельные постоянные чаты, state.db, детерминированные gates |
| Ограничения | не доказано, что есть те же автоматические guards и связи чатов | текущие ошибки протокола, разрешений, навигации, неполный bootstrap |
| Доказательства | скрин/ссылка чата, фактический вывод, отсутствие изменений | `status`, `codex-chats`, логи app-server, UI confirmation, Git diff |

**Правило выбора:** при равном результате предпочитать меньшее число технических слоёв. Если нужен строгий FSM и независимые постоянные чаты — фиксируем это как обязательное требование, сохраняем Bridge и исправляем его, а не имитируем согласования только промптами.

## Итерации реализации

### 01A. Минимальный smoke test и выбор границы

**Подготовка:** Codex App открыт на Git-корне этого репозитория; `git status` чистый; зафиксированы версии App и CLI; отчёт сохранён вне `workflow/`. Запустить нативный сценарий в текущем чате без изменения проекта. Для Bridge сначала проверить `doctor`/`codex-doctor`, права доступа к `~/.codex`, установленный пакет, потом безопасно запустить тот же текст на отдельном тестовом project-root. Если Bridge не стартует — результат `blocked`, не обходить протокол вслепую.

**Сравнить:** число ручных действий, наличие видимого результата, количество реально созданных чатов, ошибки, границы доступа, способность прервать и продолжить, наличие проверяемого approval gate. Для любой UI-навигации требуется отдельный реальный сигнал `navigated`, не просто ID чата. Принять решение A/B и сохранить в `docs/DECISIONS.md`.

### 01B. Codex transport (только если выбран Bridge)

**Затрагиваемые компоненты:** `workflow/workflow_engine/codex/client.py`, fake app-server, `test_codex_integration.py`.

- Репродукция: historical error `readOnly.access is no longer supported; use permissionProfile for restricted reads`.
- Найти реально поддерживаемую схему **у установленной версии**, провести негативный тест устаревшего поля и тест действительных ограничений. Удаление `access` само по себе не доказательство сохранения restricted reads.
- Отдельно диагностировать `~/.codex` permission failure без требования менять защищённые файлы.
- Тесты: несовместимая схема, failed app-server init, `readOnly` без записи, правильное сообщение о необходимости действия пользователя.

**Приёмка:** контракт fake-server и живой `turn/start` соответствуют установленному Codex, нет временного monkeypatch и не запрошен API key.

### 01C. Resume, idempotency, UI (только если выбран Bridge)

**Затрагиваемые компоненты:** `workflow/workflow_engine/codex/provider.py`, `threads.py`, launcher/skill, integration tests.

- Тест на прерывание **после** `thread/start`, **до** первого успешного хода: повтор не теряет роль и не дублирует pending-запрос.
- Разделить события `created`, `turn_start_unknown`, `turn_started`, `completed` так, чтобы `last_turn_id=null` не означал доказанную инициализацию роли.
- Навигация в окно возможна **только через подтверждённый UI-инструмент**, доступный запускающему чату. CLI сам не обещает переключать интерфейс. Фиксировать `opened` / `not_supported`; отдельный ID и ссылка — fallback, не подмена требования.
- Восстановление неопределённого хода — только после проверки чата, файлов и вручную выполненного явного действия.

**Приёмка:** роль восстанавливается, pending не очищается автоматически, UI явно подтверждён или ограничение показано пользователю.

### 01D. Регрессия, документы и реальная приёмка

- Сценарий S1: пустой проект + неполное задание → вопросы, не реализация.
- S2: ответы пользователя → согласованное понимание, состояние **перед** route.
- S3: отказ в правах/устаревший параметр → чёткая ошибка без ложного `completed`.
- S4: обрыв первого turn → проверка и ручной recovery, без дублирования.
- S5: если Bridge выбран, отдельный чат действительно открылся (или зафиксирована неподдерживаемость UI-операции).
- S6: `git diff --check`; unit + fake integration tests; проверка отсутствия изменения защищённого оригинала.
- S7: отчёт по `reports/_TEMPLATE.md` с версиями, воспроизведением, выводом и решением.

Приёмка **только по реальному отчёту владельца**, статус этапа в ROADMAP меняется на `verified_live/accepted` после проверки. Не интерпретировать сам `await_clarification` как баг, если вопросы действительно необходимы.

## Сигналы неисправности и действия

| Симптом | Категория | Первое действие |
|---|---|---|
| Отказ доступа к `~/.codex` | среда/права | записать stderr и контекст запуска, проверять права без отключения безопасности |
| `readOnly.access is no longer supported` | Bridge protocol | негативный тест + уточнение действующего протокола |
| Чат есть, ходов нет, `pending=1` | recovery | не повторять, инспекция истории и состояния |
| Запущен без role instructions | bootstrap | сравнить первый prompt и наличие full role после ошибки |
| Чат создан, но не открыт | UI adapter | инструмент навигации или честно сообщить fallback |
| Слова `completed`, но нет тестов | evidence | отметить как unverified, потребовать дифф/логи |
